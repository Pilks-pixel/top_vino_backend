# PostgreSQL portability and graduation

[Ticket #52](https://github.com/Pilks-pixel/top_vino_backend/issues/52) implements the portability evidence in [decision #39](https://github.com/Pilks-pixel/top_vino_backend/issues/39) and [spec #41](https://github.com/Pilks-pixel/top_vino_backend/issues/41). This work creates no AWS resource or paid backup service. **A local restore proves the stock PostgreSQL exit path; actual Neon export and Neon transaction-pool behavior remain pending until independently verified.**

## Disposable stock PostgreSQL rehearsal

Use the exact Node version in `.nvmrc`, Docker, Git and OpenSSL on a trusted workstation. Build the Linux AMD64 runtime from the complete reviewed checkout, including the #46 migration entrypoint and #50 standard release smoke:

```bash
docker build --platform linux/amd64 --target runtime -t top-vino-portability:runtime .
node scripts/verify-portability.mjs --image top-vino-portability:runtime --output /tmp/top-vino-portability-YYYYMMDD
```

The output directory must be empty, private (`0700`) and outside the checkout; exports and reports are `0600`. The command accepts no live source URL and ignores inherited database credentials. It creates only uniquely named, owned Docker containers/network, uses pinned PostgreSQL 15, generates an ephemeral CA with verified TLS, and creates separate owner/runtime roles. The final image applies committed migrations to an empty database through its normal entrypoint. Prisma's direct migration connection and bounded runtime pool both use `sslmode=require`, `sslaccept=strict` and the ephemeral trusted CA; the runtime role has DML permission on business/authentication tables, no schema creation, and no migration-table grants.

The harness creates a fixed synthetic fixture: two Users, one Public Deck, one Card, one viewer Collaborator, independent Progress and Review rows for each User, and one Answer Submission. No live data enters it. A local HTTPS gateway preserves production origins and secure-cookie semantics while the **standard #50 operator smoke** checks release identity, liveness/readiness, documentation, both schemas, synthetic sign-in, authorized Deck read and sign-out. The API process still runs with production configuration and the final non-root image; test-mode origin/authentication bypasses are not used.

The custom-format logical dump keeps schema but **excludes all data in `account`, `session`, and `verification`**, including password hashes, provider tokens, active sessions, IP/user-agent metadata and recovery/verification material. Deliberately populated private fixture rows ensure the restore verifies exclusions. Users and content in this rehearsal are generated synthetic values. The restored image receives a newly provisioned synthetic credential, not an exported password. The harness writes only sanitized summary evidence to stdout.

`synthetic.dump`, its SHA-256 sidecar, and `report.json` remain private. The report records image ID, PostgreSQL version/digest, checksum, bytes, dump/restore/total durations, schema/column/constraint/extension inventory, row counts, key invariants, and original/restored/rotated API smoke results. Restore uses a fresh owned database, `--no-owner --no-acl --exit-on-error --single-transaction`, followed by catalog/count/invariant comparison before re-provisioning authentication. Runtime credentials rotate on the original source, and host/role/password URLs change on the restored source, with the image ID unchanged. The command cleans up owned containers/network and ephemeral private files on success or failure; review any cleanup error before rerunning. Interrupted runs may leave uniquely named Docker resources; remove only that run's resources after inspecting their names.

Local pooling evidence is Prisma's bounded pool against stock PostgreSQL, **not** Neon/PgBouncer transaction pooling. A live pooled Neon runtime URL and separate direct owner URL, both TLS, must still pass the standard smoke and release gate. No provider hostname appears in application/database code; the harness deliberately uses generic `source` and `restore` hosts. Provider URLs belong to environment configuration.

Repeat the provider-neutral restore after a PostgreSQL major, schema strategy, migration-tooling or runtime-contract change, and at the durable-beta gate. Ordinary additive migrations do not require a full rehearsal every time. Small fixture timing estimates neither live volume nor a production maintenance window; measure a suitably sized sanitized rehearsal before estimating cutover time.

## Verified Neon export handoff (pending)

The operator must first finish the dashboard-owned setup in [deployment-runbook.md](./deployment-runbook.md). Run `bash scripts/prepare-neon-portability.sh` to record the target and walk this handoff. It only records non-secret target facts in a private external file; no dump or provisioning happens automatically.

1. In the Neon dashboard, verify account, project, branch, database, region, PostgreSQL major, billing/free-plan state and direct owner role against the recorded inventory. Never infer a safe target from a hostname or a User email. Keep the existing sandbox serving; do not reset it to manufacture portability evidence.
2. Use an explicitly approved **temporary synthetic-only rehearsal branch/database**, within verified free quotas, with committed migrations and the same fixed synthetic fixture contract above. Begin empty: schema and **every stored content field** must be known generated fixture data. Do not export arbitrary tester content merely because its account uses `@example.test`. If the source is not provably synthetic-only, stop; create a reviewed isolated sanitized copy instead. Record the exact project/branch/database, provenance, expected rows, and inspected schema/extensions. An approved temporary rehearsal does not become another deployed environment; delete it after evidence is retained.
3. Obtain the direct owner connection from dashboard Connection Details. Keep credentials on the trusted workstation in an external `0600` file or password-manager-backed environment; do not put URLs in command arguments, screenshots, Git, CI, or Render logs. Use libpq `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `PGSSLMODE=verify-full` and its trusted CA when required, set privately. Confirm `SELECT current_database(), current_user, version()` and exact intended target before reading data. Use the supported PostgreSQL-major `pg_dump` client. The local script deliberately cannot receive this live URL.
4. Check schema inventory against committed Prisma migrations and the expected fixture counts/invariants. Record deviations as explicit portability exceptions before export. Freeze writes to the temporary synthetic source while gathering count/invariant evidence and dumping; a changing snapshot cannot be compared to later counts reliably.
5. With `umask 077`, export from that verified source using `pg_dump --format=custom --schema=public --no-owner --no-acl --no-comments --exclude-table-data=public.account --exclude-table-data=public.session --exclude-table-data=public.verification --file=/PRIVATE/PATH/neon-synthetic.dump`. Record duration, file bytes, and `shasum -a 256 /PRIVATE/PATH/neon-synthetic.dump`. This command does not sanitize content; source provenance in step 2 and sensitive-table exclusions together establish the synthetic snapshot.
6. Restore the checksummed artifact into a **separate disposable stock PostgreSQL instance**, never the serving source, using `pg_restore --no-owner --no-acl --exit-on-error --single-transaction`. Recreate owner and least-privilege runtime roles separately. Compare schemas, columns/types/defaults, constraints, extensions/versions, each table count (excluded auth tables must contain zero rows), orphan/duplicate rows, review quality and Progress invariants. Apply only reviewed compatible migrations through the direct connection. Provision a fresh synthetic credential privately and run the same final image with TLS plus `scripts/release-smoke.mjs` against its HTTPS origin. Keep sanitized summaries/checksum/timing; never commit the dump.
7. Replace the live pooled runtime URL and direct owner URL through the reviewed rotation/release procedure, without rebuilding the image, and verify a standard smoke. Record actual transaction-pool behavior separately from the stock local test. Keep actual Neon export/pooling acceptance pending until these observations pass. Delete the temporary rehearsal source, restored instance and sensitive local credentials/artifact according to the agreed retention period; a checksum/summary may remain.

The source check, freeze, inventory comparison and standard smoke are acceptance gates, not suggestions to mark a checklist complete. If a live extension differs from the inventory below, halt and decide whether to remove it or document an intentional portability exception. Never enable a paid plan or backup product as an implicit part of this test.

## Durability and AWS gates

The operational decision #38 remains authoritative. User reliance or non-disposable data, an uptime/recovery/support promise, unmet recovery/logging need, **two user-impacting incidents in 30 days**, **more than two recovery hours in a month**, or **one quota suspension** freezes new reliance and irreplaceable data. The owner chooses the least expensive capability meeting the named need, reduces scope, changes provider, or retires the environment. It does not automatically authorize AWS. The earlier $10/month preference is not a hard post-trigger ceiling; the owner must accept a current quote for any paid change.

A durable beta may hold irreplaceable data only after **automated daily backups outside the database provider**, **RPO at most 24 hours**, a documented restore procedure and **a successful restore rehearsal**. This ticket's synthetic export is not an automated backup or proof of production recovery. Durable data forbids disposable rebuilds for schema changes; availability/log retention/support promises require their own purchased evidence.

An AWS evaluation opens only for a measured unmet customer/compliance/regional/security/network requirement, measured reliability/recovery/observability/scaling/control need, an approved component benefiting from AWS-native capability, or a **three-month total-cost forecast** plausibly meeting the migration economics. Record requirement/evidence, owner and review deadline. Traffic, account count, database size, or paying the incumbent alone are not triggers. Close an unsuccessful evaluation and choose the next review condition.

At that future evaluation, check **live Singapore-region pricing** and compare a credible AWS option with staying on the incumbent at measured current load and **3x load**. Include compute, database, storage, off-provider backup/restore, networking, public IPv4, transfer, logs, monitoring, DNS, support, tax; single-/multi-AZ failure and recovery boundaries; secrets, release/migration sequencing, security and failure modes; monthly owner time for deployment/patching/access/incidents/cost review; and one-time implementation/rehearsal/cutover/rollback work. Record assumptions and a current recurring bill accepted by the owner. No topology or dollar quote is selected prematurely here.

Actual migration requires a short-lived rehearsal of the selected topology plus either a named non-cost requirement the incumbent cannot acceptably meet, or a **six-month forecast at least 30% and $25/month cheaper**, including migration and ongoing owner time. The owner explicitly accepts recurring cost and operational burden. An AI component must pass its own gate; its benefit does not mandate moving the core API/database.

After authorization, the temporary AWS rehearsal adds IAM/secrets, VPC/security groups, regional latency, parameters/extensions, logs/alerts, deploy health/failure recovery, resource usage and live cost projection; tear it down unless migration is approved. A cutover window may be at most two hours and must intentionally lose **no acknowledged write**: announce/stop deploys, verify source write freeze, checksum final dump, restore/replay compatible migrations/check inventory/counts/invariants/full smoke, switch configuration, then reopen writes and record actual downtime/durations/cost/deviations. Before destination writes, rollback returns config to the still-frozen source. After destination writes, stop writes and recover forward under an explicit incident decision; never operate two writable sources.
